Деплой готового образа
на ssh 160

GitLab собирает и проверяет приложение, Docker Hub хранит образ, а сервер 192.168.1.160 загружает готовый артефакт и запускает его. Сборка образа, установка Python-зависимостей и collectstatic выполняются в CI.

1. Как устроен деплой

  1. 1 · GitLab mainКод, тесты, анализ исходников и зависимостей
  2. 2 · Docker HubСборка образа, публикация с тегом commit SHA
  3. 3 · Проверки CIСканирование образа, DAST и Security Gateway
  4. 4 · ssh 160Pull → бэкап → миграции → запуск → HTTP-проверки

Pipeline не подключается к локальной сети. Оператор запускает scripts/deploy_lan.py на сервере после успешного завершения CI. Само появление образа в Docker Hub ещё не означает, что проверки пройдены.

Образ: sergemmikh/thrdlabapp-devsecops-diploma:<первые 8 символов SHA>. После загрузки скрипт сверяет OCI-метку полного SHA и фиксирует repository@sha256:…. Тег latest для запуска не используется.

Контейнер работает пользователем django, с файловой системой только для чтения, временным /tmp, без Linux capabilities и с no-new-privileges. Логи ограничены тремя файлами по 10 МБ.

2. Что должно быть настроено

  • SSH-профиль 160 на компьютере оператора; пользователь сервера — smm.
  • Репозиторий /home/smm/thrdlabapp с remote gitlab: git@gitlab.com:sergeMMikh/thrdlabapp-devsecops.git. На текущем сервере fetch использует локальную настройку перенаправления на HTTPS.
  • Docker Engine, Docker Compose ≥ 2.30 и Python ≥ 3.10. Пользователь smm имеет доступ к Docker и управлению сервисом через sudo -n.
  • Доступ с сервера к GitLab API и Docker Hub. PostgreSQL pg-standalone запущен и подключён к одной Docker-сети.
  • В GitLab CI настроены DOCKERHUB_USERNAME, DOCKERHUB_TOKEN и соответствующие runner.

Сохранённый .env на сервере должен содержать GITLAB_TOKEN с правом чтения API проекта, параметры PGDATABASE, PGUSER, PGPASSWORD и действующие настройки Django. Файл исключён из Git и контекста сборки; права доступа — 600. Значения секретов в документацию и команды не копируются.

Скрипт формирует отдельный runtime env только из разрешённых параметров приложения. GitLab-токен и CI-учётные данные в контейнер не передаются. PGHOST задаётся как имя существующего контейнера БД. Сохраняйте действующий стабильный SECRET_KEY: его смена влияет на подписанные сессии.

Перед запуском предусмотрите короткое окно недоступности: приложение останавливается на время бэкапа, миграций и переключения. Для несовместимых миграций заранее нужен план восстановления БД.

3. Обновление приложения

  1. Опубликуйте изменения в main GitLab и откройте список pipeline. Дождитесь успеха всех jobs, включая сканеры с allow_failure. Возьмите числовой ID pipeline из его страницы.
  2. Подключитесь к серверу и обновите служебные файлы из той же версии кода: 
    ssh 160
cd /home/smm/thrdlabapp
git status --short
git pull --ff-only gitlab main

    Сохраните собственные изменения до обновления. Скрипт требует точного совпадения локального HEAD и SHA выбранного pipeline. Если main уже ушёл вперёд, дождитесь успешного pipeline для актуального коммита.

  3. Запустите деплой, подставив настоящий ID вместо PIPELINE_ID: 
    python3 scripts/deploy_lan.py --pipeline PIPELINE_ID

    Дождитесь завершения команды. Не запускайте одновременно второй деплой или откат.

Что делает команда

  1. Проверяет через GitLab API успешный pipeline ветки main, результаты всех jobs и совпадение SHA.
  2. Загружает образ, проверяет OCI revision и фиксирует его digest. Извлекает уже собранную статику; запускает Django check и план миграций в одноразовом контейнере.
  3. Сохраняет прежние настройки сервиса и релиза, останавливает приложение, создаёт полный дамп PostgreSQL postgres-all.sql.gz и проверяет читаемость gzip.
  4. Считает основные записи приложения, применяет миграции и повторно сверяет количества. Это контроль сохранности количества записей, а не полная проверка содержимого базы.
  5. Переключает статику, сохраняет Compose-конфигурацию и digest релиза, устанавливает systemd drop-in и запускает сервис с --no-build --pull never.
  6. Ждёт healthy именно для выбранного digest до 90 секунд, учитывая временное присутствие старого и нового контейнеров при пересоздании. Проверяет семь HTTP-адресов и сохраняет результат. Ошибка после остановки сервиса запускает восстановление прежнего приложения и статики.

На сервере не выполняются docker build, pip install или collectstatic. Миграции и служебные команды Django используют загруженный образ.

4. Проверка результата и логи

cd /home/smm/thrdlabapp
python3 scripts/deploy_lan.py --status
systemctl is-active thrdlabapp.service
systemctl is-enabled thrdlabapp.service
docker compose --project-name thrdlabapp-lan \
  --env-file .deployment/active.env -f .deployment/active.compose.yaml ps
curl --fail --silent --output /dev/null --write-out '%{http_code}\n' http://192.168.1.160/

Ожидаемые результаты: сервис active и enabled, контейнер healthy, HTTP 200. В --status видны pipeline, SHA, digest, каталог релиза, проверенные адреса и количества записей.

Автоматически проверяются /, /furnaces/, /furnaces/furnace-booking/, /furnaces/equipments/, /furnaces/equipment-booking/, /admin/login/ и /static/main/img/neon-electrochemistry-lab-badge.png. После обновления также откройте приложение в браузере и проверьте нужный пользовательский сценарий.

journalctl -u thrdlabapp.service -n 100 --no-pager
docker compose --project-name thrdlabapp-lan \
  --env-file .deployment/active.env -f .deployment/active.compose.yaml logs --tail 100 web

Где лежат состояние и резервные копии

Путь относительно проектаСодержимое
.deployment/state.jsonПоследний успешно проверенный релиз.
.deployment/active.env, active.compose.yamlDigest, пути и снимок Compose; последующий git pull не меняет активную конфигурацию сервиса.

Каталог .deployment имеет права 700, файлы с данными и настройками — 600. Не публикуйте runtime env, дампы и файлы *.before: они могут содержать секреты. Храните резервные копии отдельно от сервера по принятой политике; скрипт автоматически их не удаляет.

5. Откат

Для возврата к состоянию непосредственно перед последним успешным деплоем:

cd /home/smm/thrdlabapp
python3 scripts/deploy_lan.py --rollback
systemctl is-active thrdlabapp.service
curl --fail --silent --output /dev/null --write-out '%{http_code}\n' http://192.168.1.160/

Команда возвращает предыдущие настройки systemd, образ, runtime env, Compose-конфигурацию, статику и состояние релиза. При возврате к контейнерному релизу также ждёт его healthy, проверяет страницы и обновляет ID контейнера в состоянии. При первом переходе на контейнер сохранён прежний сервис с хостовым Python-окружением.

База данных автоматически не откатывается. Возврат старого кода безопасен только при совместимой схеме. Для несовместимой миграции восстановление из postgres-all.sql.gz планируется отдельно: оно может затронуть записи, созданные после бэкапа. Универсальная команда восстановления здесь намеренно не приводится.

После автоматического отката из-за ошибки сначала проверьте сервис и логи. Повторный ручной --rollback использует последний успешный релиз из state.json и может вернуть ещё более раннюю версию.

6. Если обновление остановилось

СитуацияДействие
Pipeline или один из jobs неуспешенИсправьте причину в GitLab и дождитесь полного успеха. Скрипт отклоняет даже сбой advisory-сканера.
Локальный SHA не совпадает с pipelineПроверьте git status, выполните fast-forward обновление и выберите pipeline этого коммита.
GitLab API отвечает 401/403Проверьте срок и доступ токена в серверном .env. Не выводите его в терминал и логи.
Ошибка pull, OCI revision или digestПроверьте доступ к Docker Hub и job сборки. Не подменяйте образ на latest вручную.
Бэкап, миграции или сверка записей не прошлиИзучите ошибку и каталог релиза. Проверьте возврат сервиса; не удаляйте дамп и не запускайте восстановление БД без плана.
Контейнер не стал healthy или HTTP-проверка не прошлаПосмотрите journal и Compose logs. Скрипт пытается восстановить прошлое приложение; подтвердите результат через сервис и браузер.
Ошибка самого восстановленияСохраните каталог неуспешного релиза и логи. Для диагностики используйте его controls.json; сначала установите фактическое состояние сервиса и БД.
